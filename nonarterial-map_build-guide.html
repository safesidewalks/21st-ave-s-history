21st Ave S · Reproduction Runbook

Building the non-arterial concrete vs. asphalt map, from scratch

This is the step-by-step record of how the SDOT non-arterial sidewalk map was made — from pulling raw geodata off Seattle’s open-data portal, through the Python pipeline, to a published, interactive Google Map. Written so you (future Dana) can rebuild or refresh it without reverse-engineering anything.

Output: protype_concrete-non-arterials_v1.html Pipeline: build_dataset.py ~58 segments citywide

Overview

The map makes one argument visually: across Seattle’s non-arterial streets, SDOT has poured permanent concrete curb & gutter in dozens of places over the last five years — while 21st Ave S is slated only for a cheap asphalt walkway. Every built segment is a clickable line on the map; 21st Ave S is flagged in red as the outlier.

Two Seattle open-data layers feed it, joined on a shared segment key:

Sidewalks (the “CDL”)

SDOT’s sidewalk inventory: surface type, curb type, install date, building program.

Sidewalks_CDL_….csv

Seattle Streets

The street centerlines: arterial classification, street type, geometry, centroid coordinates.

Seattle_Streets_1_….csv

Seattle geodata→ build_dataset.py→ segments_data.json→ map HTML→ published map

Don’t confuse the two datasets

This map uses the Sidewalks + Streets layers (what got built). That is a different source from the scroll-driven dot visualization on the main site, which uses the Seattle Transportation Plan “Missing Sidewalks” layer (what is missing — the 11,550 / Tier-1 / equity-12 numbers). Different data, different purpose.

Prerequisites

  • Python 3 with the pyproj package (used to reproject Washington State Plane coordinates to lat/lng).
  • A Google Cloud account to create a Maps JavaScript API key (Step 5). A billing account is required, but a low-traffic page stays inside the free monthly allowance.
  • The project folder, with the SeattleGeoData/ subfolder that holds build_dataset.py.

install the one dependency

pip3 install pyproj

Step 1Pull the source geodata

Download both layers as CSV from Seattle’s GIS open-data portal. These are the live pages where the data lives — both link straight to a Download panel offering CSV, GeoJSON, Shapefile, and API access:

  • Sidewalks — data-seattlecitygis.opendata.arcgis.com/datasets/SeattleCityGIS::sidewalks-1
  • Seattle Streets — data-seattlecitygis.opendata.arcgis.com/maps/SeattleCityGIS::seattle-streets

On each page: click Download, choose CSV (full dataset), and drop both files into the SeattleGeoData/ folder.

Filenames will have a hash suffix

ArcGIS Hub appends a layer ID, so you’ll get something like Sidewalks_CDL_2674137339776368979.csv and Seattle_Streets_1_-1485582646790599907.csv. That’s normal. Either keep those exact names and update the CDL / STREETS constants at the top of build_dataset.py, or rename your downloads to match what the script already expects.

Backup: the REST API

If the Hub download UI ever changes, the same data is reachable directly from the ArcGIS REST service. The build script already queries the Streets layer here for geometry:

stable REST endpoint (Seattle Streets)

https://services.arcgis.com/ZOyb2t4B0UYuYNYH/arcgis/rest/services/Seattle_Streets_1/FeatureServer/0

Append /query?where=1=1&outFields=*&f=json to pull records, or &f=csv for CSV. The org id ZOyb2t4B0UYuYNYH is SeattleCityGIS’s ArcGIS Online organization — the same one behind both pages above.

Step 2Run the build script

build_dataset.py joins the two CSVs, filters to the segments that matter, enriches each one, and writes the JSON the map reads. Run it from the data folder:

produce segments_data.json

cd SeattleGeoData
python3 build_dataset.py

It prints a per-district summary and writes segments_data.json up into the site folder. Here is exactly what it does, so you can adjust it later.

The join

Each sidewalk record carries a SEGKEY; each street carries a COMPKEY. The script keys the streets by COMPKEY and looks each sidewalk’s SEGKEY up against it — that’s how a built sidewalk inherits its street’s classification and geometry.

The filters (a row is kept only if all pass)

FilterRuleWhy
ProgramBUILDERCD in CIP-SDOT, SSRP, SDOT-SSRP, SDOTPED, ADAPROG, NSF-CRFSDOT-funded work only
RecencyINSTALL_DATE ≥ 2021-06-23“last five years” window
CategorySW_CATEGORY == BLOCKwhole-block installs, not corner ramps
Non-arterialARTCLASS == "0" on the joined streetthe core filter — residential/local streets only
Exclusionstreet name does not contain WEST MARGINALdrops 2 mislabeled arterial segments

The date window is hardcoded

The script pins “today” to 2026-06-23 and the cutoff to 2021-06-23. To refresh the map with newer data, bump TODAY and CUTOFF near the top of the file before re-running.

The enrichment (added to each kept segment)

  • Coordinates: the street centroid (GIS_MID_X/Y) is reprojected from Washington State Plane (EPSG:2926) to lat/lng (EPSG:4326) with pyproj.
  • Concrete flag (true_cg): true only when surface is PCC and curb is 410A/410B/410C. This is what separates real concrete curb & gutter (solid lines) from asphalt walkways (dotted lines).
  • Neighborhood: nearest-centroid lookup against a hand-built table — approximate, see caveats.
  • De-dupe: collapses rows sharing the same (street, install_date, length).
  • Real geometry: the true street polyline is fetched live from the Seattle Streets FeatureServer/0 by COMPKEY, so lines follow the road instead of being straight stubs.

The result is written as a JSON array of segment objects — each with surface, curb, district, length, true_cg, path, and so on.

Step 3Build the map HTML

The map is a single self-contained HTML file. The pipeline’s output becomes an inline JavaScript array near the top of the <script> block:

embed the data

const SEGMENTS = [ /* paste segments_data.json here */ ];

Everything else keys off each segment’s true_cg flag and district. The rendering conventions:

TypeLineEnd caps
Concrete curb & gutter (true_cg: true)solidfilled circle
Asphalt walkway (true_cg: false)dottedfilled diamond
21st Ave S (the CORRIDOR object)long red dashopen red diamond

Colors are keyed to council district. 21st Ave S is a separate hardcoded CORRIDOR constant (it isn’t in the built dataset because it hasn’t been built) drawn on top so it reads as the outlier. A legend on the left lets you toggle each district and surface group; clicking any segment opens an info window with its full record and a Street View button.

The map itself is created by an initMap() callback that Google’s loader script invokes once the API is ready. It sets a custom muted basemap style, plots the segments, builds the legend, tallies the sidebar counts, and fits the view to everything shown.

Step 4Preview locally

Do not double-click the file

Opening the HTML directly gives it a file:// address, and Google Maps refuses to load over file://. You get a blank map and empty counts — nothing wrong with your code. You must serve it over http://.

Start a tiny local web server from the site folder, then open the localhost URL in your browser:

serve + open

cd 21st-Ave-S_GeneratedOutput
python3 -m http.server 8000
# then open:
# http://localhost:8000/protype_concrete-non-arterials_v1.html

You should see the Seattle basemap fill with colored segments and the sidebar counts populate (e.g. 58 segments · 16,177 ft). If the sidebar shows but the map is grey, jump to Troubleshooting.

Step 5Get a Google Maps API key

The map loads Google’s JavaScript API, which needs a key. In the Google Cloud Console:

  1. Create (or pick) a project and make sure a billing account is attached.
  2. Enable the Maps JavaScript API. (Street View here uses StreetViewService / the embedded panorama, which is part of the Maps JavaScript API — no separate API to enable.)
  3. Under Credentials, create an API key.
  4. Paste it into the loader tag at the bottom of the map HTML:

the loader script (bottom of the file)

<script async
  src="https://maps.googleapis.com/maps/api/js?key=YOUR_KEY&libraries=geometry&callback=initMap">
</script>

The libraries=geometry parameter is required — the map uses it. callback=initMap is what fires your initMap() once the API finishes loading.

Step 6Publish & lock the key

Publishing is just committing the files to the GitHub Pages repo (they serve over https://, which Maps is happy with):

publish to GitHub Pages

git add protype_concrete-non-arterials_v1.html segments_data.json
git commit -m "Publish non-arterial sidewalk map"
git push

Live at safesidewalks.github.io/…/protype_concrete-non-arterials_v1.html once Pages rebuilds.

Restrict the key before you share it

Your API key sits in plain text in the page source — anyone can read it. If it’s unrestricted, someone can copy it and run up charges on your billing account. Lock it down in the Cloud Console first.

On the key’s settings page:

  • Application restrictions → Websites. Add your published domain and localhost: 
    https://safesidewalks.github.io/*
http://localhost:*
  • API restrictions. Limit the key to Maps JavaScript API only.
  • Billing. Set a budget alert or quota cap so a leaked key can’t cost real money.

Expected side effect

Once restricted to those domains, the map works on the published site and on localhost — but no longer from a random file:// open. That’s correct and intended.

Troubleshooting: a blank or grey map

Work down this list — it’s roughly most-common first.

  1. Opened as a file? If the address bar says file://, that’s the problem. Serve over http:// (Step 4).
  2. Sidebar renders but counts are empty and the map is blank? That signature means the whole <script> block died on a JavaScript syntax error — one bad character voids the entire block, so the data, legend, and map all vanish together. The classic culprit is an unescaped apostrophe inside a single-quoted string, e.g. 'You're viewing…'. Escape it as 'You\'re viewing…'.

Fast way to find a syntax error

Node can check the script without running it. Pull the script block into a .js file and run node --check file.js — it prints the exact line and character. (Or open the browser DevTools Console; the red error names the line.)

  1. RefererNotAllowedMapError in the console? The key’s website restrictions don’t include the domain you’re viewing from. Add it (Step 6), or add http://localhost:* for local testing.
  2. InvalidKeyMapError / ApiNotActivatedMapError? The key is wrong or the Maps JavaScript API isn’t enabled on that project (Step 5).
  3. Grey map, “For development purposes only” watermark? Billing isn’t enabled on the project.

Data caveats to remember

  • Neighborhood labels are approximate. Each segment is assigned to the nearest neighborhood centroid from a hand-built table — imprecise near boundaries.
  • West Marginal Way SW is excluded. Two segments there are functionally arterial and were dropped by name.
  • 1/1/YYYY install dates mean “year known, day unknown.” Many records only carry a year; the pipeline normalizes those to Jan 1 and the map labels them “(planned / day unknown)” where relevant.
  • Counts reflect what’s shown. The sidebar tally counts only concrete + asphalt-walkway segments (the two categories drawn), not every raw row.
  • The dataset is a snapshot. It reflects the Seattle open-data download date. Re-pull and re-run to refresh.

The CSV vs. the JSON

The SDOT_NonArterial_Sidewalks_LastFiveYears.csv is a human-readable table of the same segment set the pipeline produces — its columns map one-to-one to segments_data.json. The JSON is the reproducible artifact; the CSV is a convenience export.
